# CHAPTER 14 — MOTION IMPLEMENTATION STRATEGY

**Trady Perch Product Implementation Constitution · Part III: Component Architecture & Design System Implementation**

**Inherited From:** Design System Bible Chapter 15 (Motion & Timing System, in full — Mt-1 "Five Tiers, Fixed Durations, No Interpolation," Mt-2 "Entrances Decelerate, Exits Accelerate," Mt-3 "Ceremonial Is a Single-Use Curve, Reserved for the Intro," Mt-4 "Every Duration Ships With a Reduced-Motion Pair"); Motion Bible Chapters 8–9, Chapter 14 (Easing Curve Library), Chapter 17 (Animation Density & Motion Budget), Chapter 40 (Route Change Choreography), Chapters 74–81 (Motion Accessibility). Chapter 11 (Component Architecture Philosophy) and Chapter 13 (Design Token Implementation) are this chapter's direct premises.

---

## 1. INTRODUCTION

Design System Bible Chapter 15 fixed five duration tiers, two shared easing curves, and one exclusive Ceremonial curve, each with a reduced-motion companion, as concrete token values. This chapter is the mechanical bridge from those values to actual animation code: which primitive renders them, how reduced-motion is enforced automatically rather than per-component, and how Motion Bible Chapter 40's route-change choreography is implemented in whatever rendering framework Chapter 10 pins. This chapter does not re-derive a single duration or curve — those are fixed upstream and consumed here exactly as Chapter 13's token pipeline generates them.

---

## 2. MOTION TOKENS AS BUILD ARTIFACTS

Every value this chapter's code touches is generated by Chapter 13's token pipeline from the same single source that produces `core.motion-duration.*` and `core.motion-easing.*`. No animation in this codebase specifies a raw millisecond value or a raw cubic-bezier string directly — every one references a generated motion token, mechanically enforced by the same lint rule Chapter 13 §6 already applies to color and spacing literals, extended to duration and easing values.

---

## 3. THE ANIMATION PRIMITIVE

A single, shared animation utility — not one instance per component, per Chapter 1's IP3 — wraps whatever underlying animation mechanism Chapter 10 pins (CSS transitions, a JavaScript animation library, or the rendering framework's native primitive) and exposes exactly one interface: a tier name (`"instant" | "quick" | "standard" | "deliberate" | "ceremonial"`) and a direction (`"entrance" | "exit"`). The utility resolves the tier and direction to the correct duration and easing curve internally, per Mt-1 and Mt-2 — a component never selects a duration or curve independently, only a tier and a direction, which structurally makes Mt-1's "no interpolation" rule unbreakable rather than merely documented: there is no code path through which an intermediate duration could be specified.

The Ceremonial tier is gated behind a separate, explicitly named export (`useCeremonialMotion`, or equivalent) rather than exposed through the same general interface as the other four tiers — a structural enforcement of Mt-3's exclusivity, making the intro sequence's single legitimate consumer visibly distinct in code from every other, ordinary use of motion, and making a second Ceremonial consumer stand out immediately in review rather than blending in as an unremarkable tier selection.

---

## 4. REDUCED-MOTION ENFORCEMENT

Mt-4 requires every duration to ship with a reduced-motion companion, built in from the start. This chapter's animation primitive reads the user's reduced-motion preference once, centrally, at the point where a tier resolves to its actual duration and curve — never per-component, and never requiring a component author to remember to check the preference themselves. This is the direct code-level enforcement of Mt-4's own stated purpose: reduced-motion support is automatic for every future consumer of the primitive, not a parallel system requiring separate implementation per component.

A component that bypasses this primitive and implements its own animation directly — a raw CSS transition written inline, for instance — is, by definition, unable to inherit this automatic reduced-motion behavior, and is flagged by Section 7's enforcement mechanism as a Chapter 1 IP6 floor violation: reduced-motion support is a non-negotiable floor, not a convenience an individual component may skip.

---

## 5. ROUTE-CHANGE CHOREOGRAPHY

Motion Bible Chapter 40's route-change choreography is implemented as a dedicated layer sitting above individual component animations, triggered by Chapter 38's rendering-strategy routing layer rather than by any single component. This separation exists because a route transition's correct behavior depends on what is leaving and what is arriving simultaneously — information no single component, animating only itself, has access to. The specific choreography sequence is Motion Bible Chapter 40's content to specify; this chapter's contribution is the architectural seam where that sequence attaches to actual navigation events, so that once Motion Bible Chapter 40 is written, its choreography has a concrete implementation site waiting for it rather than requiring this chapter to be revisited.

---

## 6. THE ANIMATION BUDGET

Motion Bible Chapter 17's animation density and motion budget — how many simultaneous animations a single view may run, consistent with Master Vision §10.1's tier discipline — is enforced by the same shared primitive from Section 3 tracking active animation instances centrally. A component requesting a new animation while the current view's budget is already spent either queues or is denied per Motion Bible Chapter 17's specific rule, once written; this chapter's contribution is that the primitive is architected with a central registry capable of enforcing such a budget, rather than each component animating independently with no visibility into what else is currently in motion.

---

## 7. ENFORCEMENT & MEASUREMENT

An automated test, run against every component consuming the Section 3 primitive, asserts that its resolved duration and easing curve match the Chapter 13-generated token values for its declared tier within a defined tolerance — the direct mechanism behind this chapter's own success criterion. A separate CI check, per Section 4, flags any raw CSS transition or animation declaration outside the shared primitive, treating it as a reduced-motion floor violation regardless of how correct its raw values happen to be. A third check confirms the Ceremonial export from Section 3 has exactly one consumer in the codebase, failing the build if a second is introduced, mechanically enforcing Mt-3.

---

## 8. BEHAVIORAL RULES

**Before animating any element.** Its tier is selected per Design System Bible Chapter 15 §6's own decision guidance — matched to actual importance, never chosen by trial and error until a raw value "feels right."

**When an entrance and its corresponding exit are both needed.** Both are requested from the same primitive with the same tier but opposite direction, per Mt-2, never independently hand-tuned to slightly different durations.

**When a proposal suggests using Ceremonial timing outside the intro.** It is rejected per Mt-3, redirected to Deliberate, exactly as Design System Bible Chapter 15 §11 already specifies.

---

## 9. DO / DON'T

**Do** request every animation through the shared primitive by tier and direction, never by raw duration or curve value.

**Do** trust the primitive's centralized reduced-motion handling rather than adding a component-local reduced-motion check.

**Don't** write a raw CSS transition or inline animation outside the shared primitive, even for a seemingly trivial, one-off case — it silently loses Mt-4's automatic reduced-motion support.

**Don't** import the Ceremonial export for any component other than the intro sequence.

---

## 10. ANTI-PATTERNS

**The bespoke inline animation.** A component author, needing a quick visual flourish, writes a raw CSS transition directly rather than reaching for the shared primitive, reasoning that "it's just a small thing." This is dangerous because it silently defeats Mt-4's reduced-motion guarantee for that one component, invisible until a reduced-motion user actually encounters it — and per Chapter 5's F1, it also risks becoming a locally-copied pattern other components imitate once it exists as visible precedent. It is detected by Section 7's CI check flagging any animation declaration outside the shared primitive. It is fixed by migrating the animation to the primitive, selecting the tier that actually matches its importance per Design System Bible Chapter 15.

---

## 11. QUALITY ASSURANCE CHECKLIST

- [ ] Does every animation in the codebase route through the shared primitive from Section 3, with zero raw duration or curve values? *(Mt-1)*
- [ ] Do entrance and exit pairs use matching tiers with correct, opposite directions? *(Mt-2)*
- [ ] Does the Ceremonial export have exactly one consumer, the intro sequence? *(Mt-3)*
- [ ] Does reduced-motion resolve automatically for every animation, with no per-component opt-in required? *(Mt-4)*
- [ ] Does the automated duration/easing assertion pass for every animated component, within tolerance?
