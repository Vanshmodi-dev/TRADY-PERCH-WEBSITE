# CHAPTER 15 — RESPONSIVE IMPLEMENTATION STANDARD

**Trady Perch Product Implementation Constitution · Part III: Component Architecture & Design System Implementation**

**Inherited From:** Design System Bible Chapter 8 (Responsive & Breakpoint System, in full — Re-1 "Four Named Ranges, Not a Continuous Scale," Re-2 "The Smallest Viewport Is Satisfied First, Not Compressed Into," Re-3 "A Token Never Forks by Breakpoint Name," Re-4 "Foldables and Ultra-Wide Are Ranges, Not Exceptions"), Chapters 49–51 (Mobile, Tablet, Desktop Standards). Chapter 13 (Design Token Implementation) is this chapter's direct premise.

---

## 1. INTRODUCTION

Design System Bible Chapter 8 fixed four breakpoint ranges — Mobile (0px), Tablet (600px), Desktop (1024px), Wide (1440px), with content capped at 1280px per Chapter 6's grid — and the rule that a token's name never forks by breakpoint. This chapter is the code mechanism: the literal constants, the resolution strategy, and the testing discipline that make Re-3's one-name-many-resolutions rule actually true in the build, not merely true in the Bible's documentation. This chapter does not re-derive a single breakpoint value; all four are fixed exactly as Design System Bible Chapter 8 states them.

---

## 2. THE BREAKPOINT CONSTANTS

The four ranges are generated by Chapter 13's token pipeline as a single, canonical set of breakpoint constants — never hand-declared separately per app or per component, per Chapter 3's duplicate-translation prohibition:

```
core.breakpoint.mobile   = 0px
core.breakpoint.tablet   = 600px
core.breakpoint.desktop  = 1024px
core.breakpoint.wide     = 1440px
```

Every responsive value in the codebase — a spacing token's per-range resolution, a component's layout switch — resolves against these four constants exclusively. A component or stylesheet declaring its own breakpoint number is, per Section 6, treated identically to a raw color literal bypassing Chapter 13's token pipeline: an orphan, per Chapter 3.

---

## 3. TOKEN RESOLUTION, NOT TOKEN FORKING

Re-3 forbids a token's name from forking per breakpoint. This chapter's implementation mechanism is a single resolution function — given a semantic token name and the current breakpoint, it returns that token's value at that range, per Design System Bible Chapter 5's own per-breakpoint resolution table. A component references `semantic.space.padding.section-lg` exactly once in its code; the resolution mechanism, not the component, is responsible for producing 64px at Mobile and 96px at Desktop. A component author never writes `section-lg-mobile` or any breakpoint-suffixed variant name — doing so would be a direct Re-3 violation, mechanically prevented by the token pipeline generating no such forked name to reference in the first place.

---

## 4. MOBILE-FIRST IMPLEMENTATION ORDER

Re-2 requires the smallest viewport to be satisfied first, not compressed into from a desktop-first design. This chapter translates that design-priority instruction into an implementation-order rule as well, not only a design-priority one: styling and layout code is authored for `core.breakpoint.mobile` as the base case, with Tablet, Desktop, and Wide expressed as progressive overrides layered on top — never the reverse, where a desktop layout is the base and mobile styling subtracts from it. This mirrors exactly how Chapter 13's semantic tokens themselves resolve (base value, overridden upward per range) and keeps the code's authoring order structurally consistent with Design System Bible Chapter 8's own directional rule.

---

## 5. FOLDABLES AND ULTRA-WIDE

Per Re-4, no fifth breakpoint or device-specific override exists for a foldable device's unfolded width or an ultra-wide monitor — both fall naturally into the existing four ranges by width alone. This chapter's implementation reinforces this by exposing only width-based range detection to component code — no device-type detection API (user-agent sniffing, form-factor queries) is available anywhere in `packages/ui/`, structurally preventing a component from branching on assumed device category instead of actual viewport width, which is exactly the confusion Re-1's own "common misunderstanding" clause warns against.

---

## 6. ENFORCEMENT & MEASUREMENT

A lint rule flags any raw pixel breakpoint value in component code, mirroring Chapter 13 §6's token-literal check exactly. Chapter 48's visual regression suite runs every component in `packages/ui/` at all four breakpoint constants automatically, generated directly from Section 2's canonical set — a new breakpoint value would only ever be added by amending Design System Bible Chapter 8 itself and regenerating Section 2's constants, never by a component-level, one-off addition to the test matrix. This is the direct mechanism behind this chapter's own success criterion: zero manually-added, one-off viewport exceptions, because the full four-breakpoint matrix runs by default for every component with no per-component configuration required to opt in.

---

## 7. BEHAVIORAL RULES

**When implementing any new component.** Its base styling targets Mobile per Section 4, with Tablet, Desktop, and Wide layered as explicit overrides — never authored desktop-first and back-filled.

**When a component's layout genuinely needs to differ structurally between ranges** (not just resize, but rearrange), the difference is expressed through the same resolution mechanism from Section 3 driving a layout-mode prop, never through separate, range-specific component variants that duplicate logic per Chapter 5's F3.

---

## 8. DO / DON'T

**Do** author every component's base styles for Mobile first, adding Tablet/Desktop/Wide overrides progressively.

**Do** rely on the Section 3 resolution mechanism for every responsive value — never declare a breakpoint-suffixed token name.

**Don't** branch component logic on device type or user agent — only on the width-based range constants from Section 2.

**Don't** add a component-specific viewport test outside the automatic four-breakpoint matrix Section 6 already runs for every component by default.

---

## 9. ANTI-PATTERNS

**Desktop-first retrofitting.** A component built and visually verified at a wide desktop canvas first, with mobile styling patched in afterward to fix whatever breaks. This is dangerous because it reliably produces a mobile experience that merely survives rather than one genuinely designed for its constraints — exactly the failure Design System Bible Chapter 8's Re-2 and its own anti-pattern section already name. It is detected by Section 6's mandatory four-breakpoint visual regression catching layout breakage at Mobile that a desktop-first author never actually looked at during development. It is fixed by rebuilding the component's base styles mobile-first per Section 4, treating the desktop presentation as the addition, not the foundation.

---

## 10. QUALITY ASSURANCE CHECKLIST

- [ ] Does every responsive value resolve through Section 3's mechanism, with zero breakpoint-suffixed token names in use? *(Re-3)*
- [ ] Is the component's base styling authored for Mobile, with Tablet/Desktop/Wide as progressive overrides? *(Re-2)*
- [ ] Does the component avoid all device-type or user-agent branching, using only width-based range constants? *(Re-4)*
- [ ] Does the component pass visual regression at all four breakpoints from Section 2, automatically, with zero manual opt-in?
