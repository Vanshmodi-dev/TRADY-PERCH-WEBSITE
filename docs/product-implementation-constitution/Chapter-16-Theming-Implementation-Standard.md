# CHAPTER 16 — THEMING IMPLEMENTATION STANDARD

**Trady Perch Product Implementation Constitution · Part III: Component Architecture & Design System Implementation**

**Inherited From:** Design System Bible Chapter 52 (Dark Mode & Theming Architecture, in full — Dm-1 "There Is No User-Toggleable Dark/Light Mode," Dm-2 "A Light Variant, Where Genuinely Needed, Serves a Different Medium — Never a Preference," Dm-3 "Light-Variant Colors Are Newly Derived, Never a Naive Inversion"). Chapter 13 (Design Token Implementation) is this chapter's direct premise.

*A note on scope, in keeping with this Constitution's own IP1: this Constitution's Architecture document originally framed this chapter around "token-swap strategy" and "persistence of user preference," language that assumes a conventional, user-toggleable dark/light theme system. Design System Bible Chapter 52 explicitly forbids exactly that (Dm-1) — Trady Perch has one fixed, native dark identity, not a toggleable preference. This chapter follows Design System Bible Chapter 52 as the higher authority, per this Constitution's own §0.1 standing rule, rather than the Architecture document's premature assumption. The mismatch is logged in Chapter 66's Engineering Debt Register as a correction owed to this Constitution's own front matter.*

---

## 1. INTRODUCTION

Design System Bible Chapter 52 states something most design systems don't: there is no dark/light toggle to implement. The dark palette is the brand's one native identity, and a light treatment exists only where a specific medium — print, certain email clients — genuinely requires one, never as a user-facing preference. This chapter's job is correspondingly narrower than a conventional "theming system" would require: it prevents a toggle from ever being accidentally built, it ensures the single dark identity paints correctly on first load with no flash of unstyled or default content, and it implements Dm-2's medium-specific light variant as a separate, non-runtime-selectable build target.

---

## 2. THE NO-TOGGLE GUARDRAIL

Per Dm-1, no code path in `apps/marketing-site/` or `apps/client-portal/` reads or stores a user theme preference, and no component in `packages/ui/` accepts a theme prop. This is enforced structurally, not only by convention: the token pipeline from Chapter 13 generates exactly one set of color values for the primary digital surfaces — there is no second, alternate value set for those surfaces to switch between at runtime, which makes a toggle mechanically impossible to wire up correctly even if someone attempted it, rather than merely discouraged by policy.

A request to add a light-mode toggle to the Marketing Site or Client Portal is rejected outright, per Dm-1's own "no exception" clause — this is not a case Chapter 1's derivation test needs to run, because Design System Bible Chapter 52 has already, explicitly, closed it.

---

## 3. FIRST-PAINT CORRECTNESS

The requirement a conventional dark-mode chapter would call "flash of incorrect theme prevention" still has a real, narrower analog here: because there is only one theme, the failure mode is not a wrong-theme flash but an *unstyled* flash — a browser's default white background appearing for a frame before the dark identity's CSS applies, which would visually contradict Master Vision §6.1's dark-native identity at the single most visible moment, first paint.

This chapter requires the dark identity's foundational background and text-color tokens to be inlined into the initial server-rendered HTML response (per Chapter 38's rendering strategy) rather than deferred to an external stylesheet's load time — the same technique a conventional theme-flash-prevention mechanism uses, applied here to guarantee correctness against the browser's own default rendering rather than against a second, competing theme.

---

## 4. THE LIGHT-VARIANT BUILD TARGET

Per Dm-2, a light-background treatment is built only where a specific medium genuinely requires it, as a separately named build target — never as a runtime-selectable option inside the primary product. Chapter 60's print collateral is Design System Bible Chapter 52's own named example; a light-safe email-client rendering (per Dm-2's own mention of email clients defaulting to light backgrounds) is the one plausible digital case, implemented as its own dedicated template output, entirely separate from `packages/ui/`'s primary component set, and never sharing a runtime theme-switch mechanism with it.

Per Dm-3, this light variant's color values are independently defined in Chapter 13's token pipeline as their own named token set — never generated by mechanically inverting the primary dark tokens — and independently contrast-verified per Design System Bible Chapter 3's own verification standard, exactly as Design System Bible Chapter 52 §5 requires.

---

## 5. ENFORCEMENT & MEASUREMENT

A structural lint rule scans `packages/ui/` for any theme-prop pattern or `localStorage`/cookie read matching a theme-preference key, failing the build if found — the mechanical enforcement of Section 2's guardrail. An automated first-paint test, per Section 3, captures the very first rendered frame in an automated browser test and asserts it matches the dark identity's background token, not the browser's unstyled default — the direct, measurable version of this chapter's success criterion, adapted from a theme-flash measurement to an unstyled-flash measurement. A separate check confirms the light-variant token set from Section 4 shares zero token values with the primary dark set beyond values Design System Bible Chapter 3 itself designates as medium-independent (a typeface family, for instance).

---

## 6. BEHAVIORAL RULES

**When a stakeholder or feature request proposes a light-mode option.** It is declined citing Dm-1 directly, without escalating through Chapter 1's derivation test — Design System Bible Chapter 52 has already resolved this question with no stated exception.

**When a genuinely new medium requiring a light treatment is identified.** A new, separately named light-variant build target is added per Section 4, never retrofitted as an extension of the existing runtime theme (which does not exist to extend).

---

## 7. DO / DON'T

**Do** inline the dark identity's foundational tokens into the initial HTML response, guaranteeing correct first paint with no flash of unstyled content.

**Do** treat a new light-variant need (a new email client, a new print product) as its own build target with independently derived, independently verified colors.

**Don't** add a theme prop, a theme context, or any user-facing toggle to `packages/ui/` — Dm-1 forbids it without exception.

**Don't** generate a light-variant color by mechanically inverting or lightening a dark-variant value — derive and verify it independently per Dm-3.

---

## 8. ANTI-PATTERNS

**The reflexive theme toggle.** A component library scaffold, an AI agent's default assumption, or a third-party UI kit's own convention introduces a theme-switching mechanism "because that's what design systems usually have," without checking Design System Bible Chapter 52 first. This is dangerous precisely because it is the *default* assumption in most tooling, meaning it can enter the codebase through inherited boilerplate rather than a deliberate decision anyone actually reviewed and approved. It is detected by Section 5's lint rule failing the build the moment any theme-prop pattern is introduced. It is fixed by removing the mechanism entirely, not by hiding the toggle from the UI while leaving the underlying dual-theme plumbing in place.

---

## 9. QUALITY ASSURANCE CHECKLIST

- [ ] Does the codebase contain zero theme props, theme context, or stored theme-preference reads? *(Dm-1)*
- [ ] Does the first rendered frame match the dark identity's background token, with no unstyled flash? *(Section 3)*
- [ ] Is every light-variant treatment its own separately named build target, never a runtime-selectable option? *(Dm-2)*
- [ ] Are light-variant colors independently derived and contrast-verified, never a mechanical inversion of dark values? *(Dm-3)*

## 11. FUTURE EXPANSION

**Documented assumptions.** This chapter assumes Design System Bible Chapter 52's no-toggle stance remains fixed. Should Master Vision's own brand identity ever change to admit a genuine light variant as an equal, user-facing identity — a change that would itself require amending Master Vision §6.1, several levels above this Constitution's own authority — this chapter would need to be rewritten from its current, narrower premise entirely, not merely extended.
